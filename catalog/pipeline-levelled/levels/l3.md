## Level 3: when will it finish?

The release manager wants to know how long the rest of the run will take, and which chain of jobs is holding it up. The build farm has as many runners as it needs. Add:

| Method | Behaviour |
|---|---|
| `{{finish_time}}(job) → minutes or none` | Minutes from now until `{{job}}` finishes, if every unfinished job it depends on (its inputs, their inputs, and so on) starts the moment its own inputs have all finished, and takes its full minutes. Finished jobs are already done. `0` for a finished job; *none* for an unknown or stuck job. |
| `{{critical_path}}(job) → list of string` | The chain of unfinished jobs that sets `{{job}}`'s finish time, from the first one to start up to `{{job}}` itself. Start from `{{job}}` and repeatedly step to its unfinished input with the latest finish time (ties: the name that comes first), until reaching a job with no unfinished inputs. Empty for an unknown, finished or stuck job. |

Many jobs can run at once: a job that waits on several inputs starts when the slowest of them finishes. Pipelines can be hundreds of jobs deep and jobs can take up to 1,000,000 minutes, so answers must not step through the run minute by minute. Finish times stay below 2^31.

### Example

```
(jobs compile 4, bundle 6, test 10, lint 3 and release 2 minutes, linked
 compile → bundle → release, test → release, lint → release)
{{finish_time}}("release")                    → 12
{{critical_path}}("release")                  → ["compile", "bundle", "release"]   (bundle and test tie at 10)
{{finish}}("compile")                         → true
{{finish_time}}("release")                    → 12
{{critical_path}}("release")                  → ["test", "release"]
{{finish_time}}("compile")                    → 0
{{critical_path}}("compile")                  → []
{{finish_time}}("deploy")                     → none
```
