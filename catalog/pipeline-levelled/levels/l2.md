## Level 2: run order and broken links

Before a run starts, the pipeline checks its config and prints the order it will start the jobs in. Add:

| Method | Behaviour |
|---|---|
| `{{stuck}}() → list of string` | Every job whose links go round in a loop: following consumer links from the job leads back to the job itself (a job that names itself counts). These jobs can never become ready. Sorted. |
| `{{run_order}}() → list of string` | Every unfinished job that isn't stuck, in the order one runner would start them: take the ready job whose name comes first, treat it as finished at once, and repeat. Finished jobs and stuck jobs are left out. It only plans: nothing is marked finished. |

A job that feeds into a loop isn't stuck itself: it can still run, even though its consumer never will.

### Example

```
(jobs compile, docs, bundle, release, gen-a, gen-b and proto, none finished, linked
 compile → bundle → release, docs → release, gen-a → gen-b → gen-a, proto → gen-a)
{{run_order}}()                               → ["compile", "bundle", "docs", "proto", "release"]
{{stuck}}()                                   → ["gen-a", "gen-b"]
```

`bundle` comes before `docs`: it becomes ready once `compile` is treated as finished, and then it's the first ready name.
