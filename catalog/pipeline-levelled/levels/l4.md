## Level 4: warming the caches

Before a run, the build farm can pre-warm the caches of a few jobs, which makes them faster. Warm slots are limited, so the release manager asks: "with `k` warm caches, how soon can this job finish?". Add:

| Method | Behaviour |
|---|---|
| `{{set_warm}}(job, minutes) → bool` | The job takes `{{minutes}}` minutes when its cache is warm (setting it again replaces the old value). Returns `false`, changing nothing, if the job doesn't exist or `{{minutes}}` is more than its normal minutes. A job with no warm time set gains nothing from a warm cache. |
| `{{fastest_finish}}(job, k) → minutes or none` | The smallest `{{finish_time}}` of `{{job}}` you can get by warming at most `{{k}}` of the unfinished jobs it depends on, `{{job}}` itself included. A warmed job still waits for its inputs. `0` for a finished job; *none* for an unknown or stuck job. It only plans: nothing stays warmed. |

`{{k}}` (0 to 100) can be more than the number of jobs. Pipelines with thousands of jobs and `{{k}}` in the tens must still be answered quickly.

### Example

```
(jobs release 5, api 10, web 10 and schema 2 minutes, linked
 api → release, web → release, schema → api; warm times release 2, api 3, web 4, schema 3)
{{set_warm}}("schema", 3)                     → false    (schema normally takes 2)
{{finish_time}}("release")                    → 17
{{fastest_finish}}("release", 0)              → 17
{{fastest_finish}}("release", 1)              → 14       (warm release: 12 + 2)
{{fastest_finish}}("release", 2)              → 10       (warm api and web: max(2 + 3, 4) + 5)
{{fastest_finish}}("nope", 1)                 → none
```

With one warm cache, warming `api` alone doesn't help: `web` still takes 10 minutes.
