## Level 4: backups and history

Before a risky rollout the team takes a backup, and after an incident they ask "what was this set to at the time?". Add:

| Method | Behaviour |
|---|---|
| `{{backup}}({{ts}}) → string` | Saves every field that exists at `{{ts}}`, and returns the backup's id: `"b1"`, `"b2"`, `"b3"`, … in order. A backup of an empty store is fine. |
| `{{restore}}({{ts}}, {{backup_id}}) → bool` | Replaces the **whole** store with the backup's contents: fields created after the backup disappear, deleted or changed fields come back as they were. Returns `false`, changing nothing, if the backup doesn't exist. A backup can be restored any number of times; changes made after a restore never alter the backup. |
| `{{get_at}}({{ts}}, {{key}}, {{field}}, {{at_ts}}) → optional string` | What `{{get}}` would have returned at time `{{at_ts}}` (`{{at_ts}} <= {{ts}}`): the field after every operation at or before `{{at_ts}}`, with expiry judged at `{{at_ts}}`. |

**TTLs across a restore.** A backup remembers how much time each field had **left** when the backup was taken. On restore, that time restarts from the restore: a field with 7 left at the backup expires 7 after the `{{restore}}` call, even if it had already expired in between. Fields without an expiry stay without one. Fields that had expired before the backup aren't in it.

A restore is a change at time `{{ts}}` like any other: `{{get_at}}` for times before it still sees the old values.

### Example

```
{{set_with_ttl}}(5, "lock", "owner", "node-1", 10)   (expires at 15)
{{set}}(6, "lock", "zone", "z1")
{{backup}}(8)                         → "b1"          (owner has 7 left)
{{set}}(9, "lock", "zone", "z2")
{{restore}}(40, "b1")                 → true
{{remaining_ttl}}(41, "lock", "owner") → 6            (now expires at 47)
{{get}}(42, "lock", "zone")           → "z1"
{{get_at}}(43, "lock", "zone", 20)    → "z2"
{{get_at}}(44, "lock", "owner", 20)   → nothing       (expired at 15)
{{get_at}}(45, "lock", "owner", 40)   → "node-1"
```
