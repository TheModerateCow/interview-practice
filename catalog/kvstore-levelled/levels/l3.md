## Level 3: expiring fields

Some settings are temporary: leader locks, canary flags, short-lived credentials. Add:

| Method | Behaviour |
|---|---|
| `{{set_with_ttl}}({{ts}}, {{key}}, {{field}}, {{value}}, {{ttl}}) → bool` | Like `{{set}}`, but the field expires `{{ttl}}` after `{{ts}}`. `{{ttl}}` is always positive. Returns `true` if the field had no value before (an expired field counts as no value). |
| `{{remaining_ttl}}({{ts}}, {{key}}, {{field}}) → int` | Time left before the field expires. `0` if the field exists and never expires; `-1` if it doesn't exist or has expired. |

A field set at time `t` with `{{ttl}}` lives from `t` up to, but not including, `t + ttl`: at that timestamp it's gone.

An expired field behaves exactly like a field that doesn't exist, in **every** method: `{{get}}`, `{{delete}}`, `{{compare_and_set}}`, `{{scan}}`, `{{scan_prefix}}`, `{{list_keys}}` and `{{remaining_ttl}}`. A record whose fields have all expired isn't listed.

- `{{set}}` on a field replaces its value and **removes** any expiry: the field lives until deleted.
- `{{set_with_ttl}}` on a field replaces its value and sets a new expiry counted from this call.
- `{{compare_and_set}}` changes only the value: the field **keeps** its expiry.

### Example

```
{{set_with_ttl}}(10, "lock", "owner", "node-1", 5) → true
{{remaining_ttl}}(12, "lock", "owner")             → 3
{{get}}(14, "lock", "owner")                       → "node-1"
{{get}}(15, "lock", "owner")                       → nothing   (expired at 15)
{{set_with_ttl}}(16, "lock", "owner", "node-2", 5) → true      (the old value had expired)
```
