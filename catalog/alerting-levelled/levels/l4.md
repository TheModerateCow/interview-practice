## Level 4: corrections and burn-rate alerts

Two changes reach the monitor. The pipeline now replays **late and corrected samples** for minutes already behind it. And paging moves to a burn-rate alert, which fires only when a long window and a short window both burn budget fast: the long window proves the problem is real, the short one that it is still happening. Add:

| Method | Behaviour |
|---|---|
| `{{amend}}(service, minute, requests, errors) → bool` | Replaces the sample for `minute`, which must be at or before the service's latest recorded minute (a minute skipped between batches can be filled in this way). The latest recorded minute doesn't change. Returns `false`, changing nothing, if the service doesn't exist, has nothing recorded at or after `minute`, or `errors > requests`. Every method sees the new sample from then on. |
| `{{set_alert}}(service, long_window, short_window, burn) → bool` | Sets the service's alert policy, replacing any earlier one (`1 <= {{short_window}} <= {{long_window}}`, `1 <= {{burn}} <= 100`). Returns `false`, changing nothing, if the service doesn't exist or has no budget. |
| `{{alert_timeline}}(service, start, end) → list of string` | Every period inside `start..end` during which the alert fired, as `"first-last"`, earliest first. A period that runs on past either end of the range is cut at the range's edge. Empty if the service doesn't exist, has no alert policy, or the alert never fired. |

**When the alert fires.** The alert fires at minute `t` when **both** windows ending at `t` burn faster than `burn` times the budget: the last `long_window` minutes (`t - long_window + 1 .. t`) and the last `short_window` minutes. A window burns faster when `errors * 1 000 000 > requests * budget_ppm * burn` for its pooled totals; exactly at that rate doesn't count, and neither does a window with no requests. Windows reach back before `start` (earlier minutes count) but not before minute 0. The alert uses the service's budget at the time of the call.

Alert reviews replay days of history against windows that are days long.

### Example

```
(api has budget 10000 (1%) and minutes 0-9: 100 requests each, errors [0, 0, 5, 6, 0, 0, 4, 4, 0, 0])
{{set_alert}}("api", 4, 2, 2)                        → true     (both windows above 2%)
{{alert_timeline}}("api", 0, 9)                      → ["3-4"]
{{alert_timeline}}("api", 4, 9)                      → ["4-4"]  (cut at the range's start)
{{amend}}("api", 4, 100, 3)                          → true
{{alert_timeline}}("api", 0, 9)                      → ["3-4", "7-7"]
{{error_rate}}("api", 4, 4)                          → 30000
{{amend}}("api", 12, 10, 0)                          → false    (latest recorded minute is 9)
{{set_alert}}("web", 4, 2, 2)                        → false
```

At minute 5 the long window (minutes 2-5, 11 errors in 400) burns, but the short one (minutes 4-5, none) doesn't. After the correction, minute 7's long window holds 11 errors in 400 and its short window 8 in 200.
