## Level 3: expiring fields

Some settings are temporary: leader locks, canary flags, short-lived credentials. Add:

| Method | Behaviour |
|---|---|
| `SetWithTTL(ts int, key, field, value string, ttl int) bool` | Like `Set`, but the field expires `ttl` after `ts`. `ttl` is always positive. Returns `true` if the field had no value before (an expired field counts as no value). |
| `RemainingTTL(ts int, key, field string) int` | Time left before the field expires. `0` if the field exists and never expires; `-1` if it doesn't exist or has expired. |

A field set at time `t` with `ttl` lives from `t` up to, but not including, `t + ttl`: at that timestamp it's gone.

An expired field behaves exactly like a field that doesn't exist, in **every** method: `Get`, `Delete`, `CompareAndSet`, `Scan`, `ScanPrefix`, `ListKeys` and `RemainingTTL`. A record whose fields have all expired isn't listed.

- `Set` on a field replaces its value and **removes** any expiry: the field lives until deleted.
- `SetWithTTL` on a field replaces its value and sets a new expiry counted from this call.
- `CompareAndSet` changes only the value: the field **keeps** its expiry.

### Example

```
SetWithTTL(10, "lock", "owner", "node-1", 5) -> true
RemainingTTL(12, "lock", "owner")            -> 3
Get(14, "lock", "owner")                     -> "node-1", true
Get(15, "lock", "owner")                     -> "", false   (expired at 15)
SetWithTTL(16, "lock", "owner", "node-2", 5) -> true        (the old value had expired)
```
